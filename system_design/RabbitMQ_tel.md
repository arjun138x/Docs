This structured, 5-phase roadmap takes you from foundational messaging concepts to enterprise-grade production setups with RabbitMQ.

---

## [**Phase 1: Foundations & Core Concepts**](#1-foundations--core-concepts)

- **Core Mental Model:** Understand message brokers vs. HTTP REST APIs, synchronous vs. asynchronous processing, and decoupling microservices.
- **Architecture Elements:**
- **Producer:** Emits messages.
- **Queue:** In-memory or disk-backed buffer storing messages.
- **Consumer:** Receives and processes messages.
- **Broker:** The RabbitMQ node orchestrating traffic.

- **Protocol Basics:** Introduction to AMQP 0-9-1 (connections, channels, frames).
- **Hands-on Setup:** Run RabbitMQ locally using Docker (`docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:management`). Learn the Web Management Console.

## [**Phase 2: Messaging Patterns & Exchanges**](#2-messaging-patterns--exchanges)

- **Direct Exchanges:** Direct point-to-point routing based on exact `routing_key` matches.
- **Fanout Exchanges:** Publish/Subscribe model where messages broadcast to all bound queues, ignoring keys.
- **Topic Exchanges:** Routing based on wildcard pattern matching (`*` for one word, `#` for zero or more words).
- **Headers Exchanges:** Advanced routing based on message header attributes rather than keys.
- **Work Queues:** Competing consumers pattern, round-robin dispatching, and task distribution.

## [**Phase 3: Reliability & Message Guarantees**](#3-reliability--message-guarantees)

- **Delivery Reliability:**
- Producer Confirms & Publisher Returns (handling unroutable messages).
- Consumer Acknowledgments (`ack`, `nack`, `reject`) and auto-ack vs. manual ack.

- **Persistence & Durability:**
- Durable Exchanges and Queues vs. Transient ones.
- Persistent Messages (disk delivery write-ahead log).

- **Fault Handling:**
- **Dead Letter Exchanges (DLX):** Rerouting expired, rejected, or failed messages.
- **Message TTL & Queue Limits:** Managing message expiration and overflow behavior.
- Retry policies with backoff strategies.

## [**Phase 4: Advanced Architecture & Tuning**](#4-advanced-architecture--tuning)

- **Modern Queue Types:**
- **Quorum Queues:** Raft-based consensus queues designed for high availability (replaces legacy mirrored queues).
- **Stream Queues:** Append-only logs for non-destructive reading, replayability, and high-throughput scenarios (similar to Kafka).

- **Performance Tuning:**
- **Prefetch Count (`qos`):** Controlling consumer backpressure and unacked message limits.
- Channel management and connection pooling.
- Batching publishes and acknowledgments.

- **Microservice Integration Patterns:** Request-Reply (RPC style over AMQP), Saga pattern orchestration/choreography, and Event-Driven Architecture.

## [**Phase 5: Production Operations & DevOps**](#5-production-operations--devops)

- **Clustering & High Availability:** Multi-node cluster design, network partitions (split-brain scenarios), and pause-minority recovery policies.
- **Federation & Shovel Plugins:** Replicating messages across data centers and distinct RabbitMQ clusters.
- **Monitoring & Security:**
- Prometheus and Grafana integration for metrics (queue depth, publish/consume rates, memory alarms).
- TLS/SSL encryption, VHosts (virtual hosts isolation), and RBAC user permissions.

# 1: Foundations & Core Concepts

RabbitMQ నేర్చుకోవడానికి **Phase 1 (Foundations & Core Concepts)** చాలా ముఖ్యం. ఇది దీనికి పునాది లాంటిది. మీరు ఇచ్చిన టాపిక్స్ ని తెలుగులో చాలా సులభంగా, రియల్-వరల్డ్ ఉదాహరణలతో అర్థం చేసుకుందాం!

---

## 1. Core Mental Model (మొథటి భావన)

### Message Brokers vs. HTTP REST APIs

- **HTTP REST API (Synchronous / తక్షణమే):** ఇది ఒక ఫోన్ కాల్ లాంటిది. మీరు కాల్ చేసినప్పుడు అవతలి వ్యక్తి వెంటనే ఆన్సర్ చేయాలి. ఒకవేళ సర్వర్ బిజీగా ఉంటే, మీకు ఎర్రర్ వస్తుంది లేదా లోడింగ్ అవుతూ ఉంటుంది.
- **Message Broker (Asynchronous / తర్వాత జరిగే ప్రక్రియ):** ఇది ఒక వాట్సాప్ మెసేజ్ లేదా పోస్ట్ ఆఫీస్ లెటర్ లాంటిది. మీరు మెసేజ్ పంపి మీ పని మీరు చేసుకోవచ్చు. అవతలి వ్యక్తి ఎప్పుడైతే ఫ్రీ అవుతారో, అప్పుడు ఆ మెసేజ్ చూసి పని పూర్తి చేస్తారు. **RabbitMQ** అనేది ఒక మెసేజ్ బ్రోకర్.

### Synchronous vs. Asynchronous Processing

- **Synchronous (సమకాలీన):** ఒక టాప్ పూర్తి అయితేనే, తర్వాతి టాప్ స్టార్ట్ అవుతుంది. దీనివల్ల మధ్యలో ఎక్కడైనా సర్వర్ డౌన్ అయితే మొత్తం సిస్టమ్ ఆగిపోతుంది.
- **Asynchronous (అసమకాలీన):** పనులను క్యూ (Queue) లో పెడతారు. సిస్టమ్ తన వేగంతో వాటిని ఒక్కొక్కటిగా పూర్తి చేస్తుంది. దీనివల్ల సిస్టమ్ ఎప్పుడూ స్లో అవ్వదు.

### Decoupling Microservices (మైక్రోసర్వీసెస్ మధ్య దూరం తగ్గించడం)

- పెద్ద అప్లికేషన్లను చిన్న చిన్న సర్వీసెస్ (Microservices) గా విడగొడతాం. ఈ సర్వీసెస్ అన్నీ నేరుగా ఒకదానితో ఒకటి మాట్లాడుకుంటే ఇబ్బంది అవుతుంది.
- RabbitMQ మధ్యలో ఉండి, ఒక సర్వీస్ పంపిన సమాచారాన్ని తీసుకొని మరో సర్వీస్ కి సురక్షితంగా అందిస్తుంది. దీనివల్ల ఒక సర్వీస్ ఆగిపోయినా మిగతా వాటికి ఎలాంటి ఇబ్బంది ఉండదు.

---

## 2. Architecture Elements (ఆర్కిటెక్చర్ అంశాలు)

### Producer (సమాచారం పంపేవారు)

- **ప్రొడ్యూసర్** అంటే మెసేజ్‌లను క్రియేట్ చేసి పంపే అప్లికేషన్ లేదా కోడ్.
- _ఉదాహరణ:_ మీరు ఆన్‌లైన్ షాపింగ్ యాప్‌లో 'Buy Now' క్లిక్ చేసినప్పుడు, మీ ఆర్డర్ వివరాలను RabbitMQ కి పంపే యాప్ పార్ట్ ప్రొడ్యూసర్ అవుతుంది.

### Queue (క్యూ / సమాచారాన్ని భద్రపరిచే ప్రదేశం)

- **క్యూ** అనేది ప్రొడ్యూసర్ పంపిన మెసేజ్‌లను వరుసక్రమంలో (FIFO - First In, First Out) భద్రపరిచే ఒక బఫర్ (Buffer). ఇది రామ్ (RAM) లో లేదా హార్డ్ డిస్క్ లో స్టೋರ್ అయి ఉంటుంది.
- కన్జ్యూమర్ (Consumer) వచ్చి ఆ మెసేజ్‌ని తీసుకునే వరకు ఈ క్యూ లోనే మెసేజ్‌లు సురక్షితంగా ఉంటాయి.

---

మనం RabbitMQ లోని **Phase 1** లోని మిగిలిన ముఖ్యమైన అంశాలను కూడా చాలా సులభంగా తెలుగులో అర్థం చేసుకుందాం!

## 3. Architecture Elements (కొనసాగింపు)

### Consumer (సమాచారాన్ని స్వీకరించి పని చేసేవారు)

- **కన్జ్యూమర్** అనేది క్యూ (Queue) లో ఉన్న మెసేజ్‌లను తీసుకుని, వాటిని ప్రాసెస్ (పూర్తి) చేసే అప్లికేషన్ లేదా కోడ్.
- _ఉదాహరణ:_ మనం ముందు ఉదాహరణలో చూసిన 'Buy Now' ఆర్డర్ మెసేజ్‌ని క్యూ నుండి తీసుకుని, బిల్లింగ్ లేదా షిప్పింగ్ ప్రాసెస్ చేసే సిస్టమ్‌ని **కన్జ్యూమర్** అంటారు.

### Broker (రాబిట్ఎమ్‌క్యూ నోడ్ / ట్రాఫిక్ మేనేజర్)

- **బ్రోకర్** అనేది RabbitMQ సర్వర్ మొత్తం. ఇది ప్రొడ్యూసర్స్ నుండి మెసేజ్‌లను స్వీకరించి, సరైన క్యూలకు పంపడం, కన్జ్యూమర్‌లకు అందేలా ట్రాఫిక్‌ని మేనేజ్ చేయడం లాంటి అన్ని పనులను చూసుకుంటుంది.

## 4. Protocol Basics (ప్రొటోకాల్ ప్రాథమిక అంశాలు)

### AMQP 0-9-1 (Advanced Message Queuing Protocol)

- RabbitMQ పనిచేయడానికి ఒక నిర్దిష్టమైన భాష లేదా నియమాల సమితి (Protocol) కావాలి. అదే **AMQP**. ఇది అప్లికేషన్ల మధ్య మెసేజ్‌లు ఎలా పంపుకోవాలో నిర్ణయిస్తుంది. దీనిలో కొన్ని ముఖ్యమైన భాగాలున్నాయి:
- **Connections (కనెక్షన్‌లు):** మీ అప్లికేషన్‌కి RabbitMQ బ్రోకర్‌కి మధ్య ఏర్పడే TCP నెట్‌వర్క్ కనెక్షన్.
- **Channels (చానెల్స్):** ఒకే కనెక్షన్ లోపల ఉండే చిన్న వర్చువల్ కనెక్షన్‌లు. ప్రతిసారీ కొత్త కనెక్షన్ ఓపెన్ చేయకుండా, ఒకే కనెక్షన్‌లో చానెల్స్ ద్వారా వేర్వేరు మెసేజ్‌లు పంపవచ్చు (ఇది సర్వర్ మీద భారాన్ని తగ్గిస్తుంది).
- **Frames (ఫ్రేమ్స్):** డేటాని చిన్న చిన్న భాగాలుగా (Packets లాగా) మార్చి నెట్‌వర్క్ లో పంపడాన్ని ఫ్రేమ్స్ అంటారు.

## 5. Hands-on Setup & Docker (ప్రాక్టికల్ సెటప్)

మీ కంప్యూటర్‌లో RabbitMQ ని రన్ చేయడానికి **Docker** అత్యంత సులువైన మార్గం. టెర్మినల్ లేదా కమాండ్ ప్రాంప్ట్‌లో కింద ఇచ్చిన కమాండ్ రన్ చేస్తే చాలు:

```bash
docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:management

```

- **-d:** బ్యాక్‌గ్రౌండ్‌లో రన్ అవ్వడానికి.
- **-p 5672:5672:** అప్లికేషన్స్ RabbitMQ తో మాట్లాడటానికి వాడే మెయిన్ పోర్ట్.
- **-p 15672:15672:** మనం బ్రౌజర్‌లో మేనేజ్‌మెంట్ డ్యాష్‌బోర్డ్ చూసే పోర్ట్ (`rabbitmq:management` ఇమేజ్ వాడటం వల్ల ఇది వస్తుంది).

### Web Management Console (వెబ్ మేనేజ్‌మెంట్ కన్సోల్)

- డోకర్ రన్ అయిన తర్వాత, మీ బ్రౌజర్‌లో `http://localhost:15672` ఓపెన్ చేయండి.
- డిఫాల్ట్ యూజర్‌నేమ్ మరియు పాస్‌వర్డ్ రెండు **`guest`** అని ఇస్తే లాగిన్ అవ్వవచ్చు.
- ఇక్కడ నుండి మీరు క్యూలు (Queues), ఎక్స్ఛేంజెస్ (Exchanges), మరియు కనెక్షన్‌లను గ్రాఫికల్ రూపంలో ఈజీగా మానిటర్ చేయవచ్చు.

# 2: Messaging Patterns & Exchanges

RabbitMQ లో చాలా ముఖ్యమైన మరియు ఇంట్రెస్టింగ్ అయిన **Phase 2 (Messaging Patterns & Exchanges)** కి వచ్చేసాం! ఇక్కడే RabbitMQ అసలు మ్యాజిక్ ఏంటో మనకు అర్థమవుతుంది.

ప్రొడ్యూసర్లు నేరుగా క్యూకి మెసేజ్ పంపకుండా, మధ్యలో ఒక **Exchange** కి పంపిస్తారు. ఆ ఎక్స్ఛేంజ్ రకరకాల రూల్స్ ఆధారంగా మెసేజ్‌లను సరైన క్యూలకు పంచుతుంది. అవేంటో తెలుగులో ఉదాహరణలతో చూద్దాం!

---

## 1. Direct Exchanges (డైరెక్ట్ ఎక్స్ఛేంజ్)

- **పనితీరు:** ఇది ఖచ్చితమైన మ్యాచ్ (Exact Match) ఆధారంగా పనిచేస్తుంది. ప్రొడ్యూసర్ పంపిన `routing_key` మరియు క్యూ బైండ్ అయిన `routing_key` సరిగ్గా మ్యాచ్ అయితేనే మెసేజ్ ఆ క్యూకి వెళ్తుంది.
- _ఉదాహరణ:_ ఒక లాగింగ్ సిస్టమ్ అనుకుందాం.
- ఎర్రర్ మెసేజ్‌ల కోసం `error` అనే రూటింగ్ కీ ఉంటే, కేవలం ఎర్రర్ క్యూ మాత్రమే ఆ మెసేజ్‌ని తీసుకుంటుంది.
- ఇన్ఫో మెసేజ్‌ల కోసం `info` అనే రూటింగ్ కీ ఉంటే, ఇన్ఫో క్యూ తీసుకుంటుంది.

## 2. Fanout Exchanges (ఫ్యానౌట్ ఎక్స్ఛేంజ్ - పబ్లిష్/సబ్‌స్క్రైబ్ మోడల్)

- **పనితీరు:** ఇది ఒక మైక్ అనౌన్స్‌మెంట్ లేదా వాట్సాప్ బ్రాడ్‌కాస్ట్ లాంటిది. ఇక్కడ `routing_key` తో సంబంధం లేదు. ఎక్స్ఛేంజ్ కి ఏ మెసేజ్ వచ్చినా, దానికి కనెక్ట్ అయి ఉన్న (Bound) **అన్ని క్యూలకి** ఆ మెసేజ్ కాపీ అయి వెళ్తుంది.
- _ఉదాహరణ:_ ఒక న్యూస్ యాప్ లో "Breaking News" రాగానే, యాప్ వాడే ప్రతి యూజర్ యొక్క క్యూకి ఆ నోటిఫికేషన్ వెళ్లాలి. ఇక్కడ ఫ్యానౌట్ ఎక్స్ఛేంజ్ పర్ఫెక్ట్ గా సరిపోతుంది.

## 3. Topic Exchanges (టాపిక్ ఎక్స్ఛేంజ్ - వైల్డ్‌కార్డ్ మ్యాచింగ్)

- **పనితీరు:** ఇది డీసెంట్ మరియు పవర్‌ఫుల్ ఎక్స్ఛేంజ్. ఇక్కడ రూటింగ్ కీస్ డాట్స్ (`.`) తో వేరు చేయబడి ఉంటాయి మరియు మనం వైల్డ్‌కార్డ్స్ (`*` లేదా `#`) వాడవచ్చు:
- **`*` (Asterisk):** సరిగ్గా **ఒక పదాన్ని** (word) మాత్రమే మ్యాచింగ్ చేయడానికి వాడతారు.
- **`#` (Hash):** సున్నా లేదా **అంతకంటే ఎక్కువ పదాలను** (zero or more words) మ్యాచింగ్ చేయడానికి వాడతారు.

- _ఉదాహరణ:_ ఆర్డర్స్ డేటా అనుకోండి (`region.product.action` లాగా).
- రూటింగ్ కీ: `india.electronics.placed`
- మీరు ఒకవేళ `*.electronics.*` అని బైండ్ చేస్తే, దేశంతో సంబంధం లేకుండా ఎలక్ట్రానిక్స్ కేటగిరీకి చెందిన అన్ని యాక్షన్ మెసేజ్‌లు ఆ క్యూకి వస్తాయి.

---

RabbitMQ లెర్నింగ్‌లో మనం ఇప్పుడు **Phase 2** లోని మిగిలిన ముఖ్యమైన అంశాలు మరియు **Phase 3** లోకి అడుగుపెట్టాము. వీటిని చాలా సులభంగా అర్థం చేసుకుందాం!

---

## 4. Headers Exchanges (హెడర్స్ ఎక్స్ఛేంజ్)

- **పనితీరు:** ఇంతకు ముందు మనం చూసిన రూటింగ్ కీస్ (routing keys) బదులుగా, ఈ ఎక్స్ఛేంజ్ మెసేజ్ యొక్క **హెడర్ ఆట్రిబ్యూట్స్ (Header attributes - key-value pairs)** ఆధారంగా రూటింగ్ చేస్తుంది.
- **రకాలు (x-match):** ఇందులో రెండు మెయిన్ రూల్స్ ఉంటాయి:
- `x-match: all` - మెసేజ్ హెడర్ లో ఉన్న అన్ని కండిషన్స్ మ్యాచ్ అయితేనే క్యూకి వెళ్తుంది (AND ఆపరేటర్ లాగా).
- `x-match: any` - హెడర్ లో ఏదో ఒక కండిషన్ మ్యాచ్ అయినా సరే మెసేజ్ క్యూకి వెళ్తుంది (OR ఆపరేటర్ లాగా).

- _ఉదాహరణ:_ ఒక PDF లేదా Image ఫైల్ ప్రాసెసింగ్ అనుకోండి. హెడర్‌లో `format=pdf` మరియు `color=true` అని పంపి, ఆ కాంబినేషన్ ఉన్న క్యూకి మాత్రమే రూట్ చేయాలనుకున్నప్పుడు ఇది చాలా ఉపయోగపడుతుంది.

---

## 5. Work Queues (వర్క్ క్యూలు / టాప్ డిస్ట్రిబ్యూషన్)

ఒక క్యూలో చాలా మెసేజ్‌లు ఉన్నప్పుడు, వాటిని ఒక్కడే కన్జ్యూమర్ ప్రాసెస్ చేయడం కష్టం. అందుకే బహుళ కన్జ్యూమర్‌లను వాడతాం. దీని గురించిన ముఖ్యమైన పాయింట్స్:

### Competing Consumers Pattern (పోటీ పడే కన్జ్యూమర్‌లు)

- ఒకే క్యూ నుండి మెసేజ్‌లను తీసుకోవడానికి একাধিক (multiple) కన్జ్యూమర్‌లు పోటీ పడుతుంటారు. అయితే ఒక మెసేజ్ కేవలం **ఒకే ఒక కన్జ్యూమర్‌కి** మాత్రమే వెళ్తుంది (డూప్లికేట్ అవ్వదు). దీనివల్ల పని త్వరగా పూర్తవుతుంది.

### Round-Robin Dispatching (రౌండ్-రాబిన్ పంపిణీ)

- RabbitMQ డిఫాల్ట్‌గా క్యూలోని మెసేజ్‌లను కన్జ్యూమర్‌ల అందరికీ సమానంగా, వరుసక్రమంలో పంచుతుంది. (ఉదాహరణకి: మెసేజ్ 1 -> కన్జ్యూమర్ A, మెసేజ్ 2 -> కన్జ్యూమర్ B, మెసేజ్ 3 -> కన్జ్యూమర్ A, ఇలా).

### Task Distribution (టాస్క్ పంపిణీ)

- ఒక పెద్ద అప్లికేషన్‌లో రకరకాల హెవీ టాస్క్‌లు (যেমন: వీడియో ఎన్కోడింగ్, ఇమెయిల్స్ బల్క్ సెండింగ్) ఉన్నప్పుడు, వాటిని వర్క్ క్యూల ద్వారా విడగొట్టి వేర్వేరు సర్వర్లకి లేదా వర్కర్స్‌కి డిస్ట్రిబ్యూట్ చేస్తారు. దీనివల్ల సిస్టమ్ ఎక్కడా హ్యాంగ్ అవ్వకుండా స్మూత్‌గా రన్ అవుతుంది.

---

# 3: Reliability & Message Guarantees

RabbitMQ లెర్నింగ్‌లో అత్యంత కీలకమైన **Phase 3 (Reliability & Message Guarantees - విశ్వసనీయత మరియు గ్యారెంటీలు)** కి వచ్చేశాం! మనం పంపే మెసేజ్ ఎక్కడా మిస్ అవ్వకుండా, సరిగ్గా గమ్యస్థానానికి చేరేలా చూసుకోవడానికి ఈ కాన్సెప్ట్స్ చాలా ముఖ్యం. వీటిని తెలుగులో సులభంగా చూద్దాం!

---

## 1. Delivery Reliability (మెసేజ్ డెలివరీ విశ్వసనీయత)

### Producer Confirms & Publisher Returns

ప్రొడ్యూసర్ ఒక మెసేజ్‌ని RabbitMQ కి పంపిన తర్వాత, అది నిజంగా బ్రోకర్‌కి చేరిందా లేదా అని కన్ఫర్మ్ చేసుకోవాలి.

- **Producer Confirms:** ప్రొడ్యూసర్ పంపిన మెసేజ్‌ని RabbitMQ విజయవంతంగా స్వీకరించిన తర్వాత ప్రొడ్యూసర్‌కి ఒక `ACK` (Acknowledgment) పంపుతుంది. దీనివల్ల మెసేజ్ పోలేదనే టెన్షన్ ఉండదు.
- **Publisher Returns:** ఒకవేళ ప్రొడ్యూసర్ పంపిన మెసేజ్, తప్పుడు రూటింగ్ కీ కారణంగా ఏ క్యూకి కూడా మ్యాప్ అవ్వకపోతే (Unroutable message), RabbitMQ ఆ మెసేజ్‌ని మళ్ళీ ప్రొడ్యూసర్‌కే వెనక్కి పంపుతుంది. అప్పుడు ప్రొడ్యూసర్ దాన్ని సరిదిద్దుకోవచ్చు.

### Consumer Acknowledgments (ack, nack, reject)

కన్జ్యూమర్ ఒక మెసేజ్‌ని క్యూ నుండి తీసుకున్న తర్వాత, అది సరిగ్గా ప్రాసెస్ అయిందా లేదా అని RabbitMQ కి చెప్పాలి.

- **ACK (Acknowledgment):** "నేను మెసేజ్ విజయవంతంగా ప్రాసెస్ చేశాను, ఇక దీన్ని క్యూ నుండి డిలీట్ చేయవచ్చు" అని కన్జ్యూమర్ బ్రోకర్‌కి చెప్పడం.
- **NACK (Negative Acknowledgment):** "ఈ మెసేజ్ ప్రాసెస్ చేయడంలో ప్రాబ్లమ్ వచ్చింది, దీన్ని మళ్ళీ క్యూలో పెట్టು లేదా రీ-ట్రై చేయి" అని చెప్పడం.
- **Reject:** మెసేజ్ సరిగ్గా లేదు, దీన్ని పడేయి (లేదా Dead Letter కి పంపు) అని చెప్పడం.
- **Auto-Ack vs Manual Ack:**
- _Auto-Ack:_ కన్జ్యూమర్ మెసేజ్ తీసుకోగానే RabbitMQ దాన్ని ఆటోమేటిక్‌గా డిలీట్ చేస్తుంది. ఒకవేళ కన్జ్యూమర్ ప్రాసెస్ చేసేటప్పుడే క్రాష్ అయితే, ఆ మెసేజ్ శాశ్వతంగా పోతుంది.
- _Manual Ack:_ ప్రాసెసింగ్ విజయవంతంగా పూర్తయిన తర్వాతే కన్జ్యూమర్ స్వయంగా `ACK` ఇస్తాడు. ఇది చాలా సురక్షితమైన పద్ధతి.

---

## 2. Persistence & Durability (శాశ్వతత్వం మరియు నిలకడ)

RabbitMQ సర్వర్ అకస్మాత్తుగా రీస్టార్ట్ అయితే లేదా కరెంట్ పోతే డేటా పోకుండా ఉండటానికి ఇవి వాడతారు.

### Durable vs Transient (Queues & Exchanges)

- **Durable:** ఇవి డిస్క్ (Disk) లో సేవ్ అవుతాయి. RabbitMQ సర్వర్ రీస్టార్ట్ అయినా సరే, ఈ ఎక్స్ఛేంజెస్ మరియు క్యూలు అలాగే ఉంటాయి.
- **Transient (Non-Durable):** ఇవి కేవలం రామ్ (RAM - Memory) లో మాత్రమే ఉంటాయి. సర్వర్ రీస్టార్ట్ అయితే ఇవి డిలీట్ అయిపోతాయి.

### Persistent Messages (డిస్క్ రైట్-హెడ్ లాగ్)

- క్యూలు డ్యూరబుల్ అయినంత మాత్రాన సరిపోదు, మెసేజ్‌లు కూడా **Persistent** గా మార్చాలి.
- ప్రొడ్యూసర్ మెసేజ్ పంపేటప్పుడు దాన్ని పర్సిస్టెంట్ మోడ్‌లో పంపిస్తే, RabbitMQ దాన్ని హార్డ్ డిస్క్‌లోని లాగ్ ఫైల్స్‌లో (Disk write-ahead log) రాసుకుంటుంది. దీనివల్ల ఒకవేళ బ్రోకర్ క్రాష్ అయినా, రీస్టార్ట్ అయిన తర్వాత డిస్క్ నుండి డేటాను మళ్ళీ రికవర్ చేసుకోవచ్చు.

---

మనం RabbitMQ లెర్నింగ్‌లో చాలా కీలకమైన **Fault Handling (లోపాలను సరిచేసే విధానం)** భాగానికి వచ్చాము. సిస్టమ్‌లో ఏదైనా తప్పు జరిగినప్పుడు లేదా మెసేజ్ ఫెయిల్ అయినప్పుడు దాన్ని ఎలా హ్యాండిల్ చేయాలో ఈ టాపిక్స్ ద్వారా నేర్చుకుంటాం. వీటిని తెలుగులో సులభంగా చూద్దాం!

---

## 1. Dead Letter Exchanges (DLX - డెడ్ లెటర్ ఎక్స్ఛేంజ్)

- **పనితీరు:** ఒక క్యూలోని మెసేజ్ ప్రాసెస్ అవ్వకుండా ఫెయిల్ అయితే, లేదా రిజెక్ట్ అయితే, ఆ మెసేజ్‌లను నేరుగా డిలీట్ చేయకుండా భద్రపరిచే ఒక ప్రత్యేకమైన ఎక్స్ఛేంజే ఈ **DLX**.
- మెసేజ్‌లు ఎప్పుడు DLX కి వెళ్తాయి?

1. కన్జ్యూమర్ ఆ మెసేజ్‌ని `NACK` లేదా `Reject` చేసి, మళ్ళీ క్యూలో పెట్టవద్దు (`requeue=false`) అని చెబితే.
2. మెసేజ్ యొక్క గడువు (TTL) ముగిసిపోతే.
3. క్యూ నిండిపోయి (Queue overflow) ఇక పట్టుకోలేనప్పుడు.

- _ఉదాహరణ:_ పేమెంట్ ఫెయిల్ అయిన ఆర్డర్స్‌ని ఒక 'Dead Letter Queue' లోకి పంపి, ఆ తర్వాత టెక్నికల్ టీమ్ వాటిని మళ్ళీ చెక్ చేయడానికి ఇది వాడతారు.

---

## 2. Message TTL & Queue Limits (మెసేజ్ కాలపరిమితి మరియు క్యూ పరిమితులు)

### Message TTL (Time-To-Live)

- ఒక మెసేజ్ క్యూలో ఎంతకాలం ఉండవచ్చో నిర్ణయించే గడువు కాలం (TTL).
- ఉదాహరణకు, ఒక ఓటీపీ (OTP) మెసేజ్ కేవలం 2 నిమిషాలు మాత్రమే వ్యాలిడ్ అనుకోండి. ఆ టైమ్‌లోగా కన్జ్యూమర్ దాన్ని తీసుకోకపోతే, ఆ మెసేజ్ ఆటోమేటిక్‌గా ఎక్స్‌పైర్ అయిపోతుంది (ఆ తర్వాత అది DLX కి వెళ్తుంది). దీన్ని మిల్లీసెకండ్లలో సెట్ చేయవచ్చు.

### Queue Limits (క్యూ పరిమితులు)

- క్యూలో గరిష్టంగా ఎన్ని మెసేజ్‌లు ఉండవచ్చో (Max Length) లేదా టోటల్ సైజ్ ఎంత ఉండవచ్చో పరిమితి పెట్టడం.
- క్యూ నిండిపోయిన తర్వాత కొత్తగా వచ్చే మెసేజ్‌లను ఏం చేయాలి? (Overflow Behavior):
- పాత మెసేజ్‌లను తొలగించడం (Drop/Reject).
- లేదా కొత్త మెసేజ్‌లను నేరుగా Dead Letter Exchange కి పంపడం.

---

## 3. Retry Policies with Backoff Strategies (రీ-ట్రై పాలసీలు మరియు బ్యాక్‌ఆఫ్)

- ఒక మెసేజ్ ప్రాసెస్ అయ్యేటప్పుడు డేటాబేస్ డౌన్ అవ్వడం వల్లనో లేదా నెట్‌వర్క్ ప్రాబ్లమ్ వల్లనో ఫెయిల్ అవ్వొచ్చు. వెంటనే మళ్ళీ రీ-ట్రై చేస్తే మళ్ళీ ఫెయిల్ అయ్యే ఛాన్స్ ఉంది.
- అందుకే **Backoff Strategy** వాడతారు:
- **Exponential Backoff:** మొదటిసారి ఫెయిల్ అయితే 2 సెకండ్లు ఆగి రీ-ట్రై చేయడం, రెండోసారి అయితే 4 సెకండ్లు, మూడోసారి అయితే 8 సెకండ్లు... ఇలా సమయాన్ని రెట్టింపు చేసుకుంటూ పోవడం.
- దీనివల్ల సర్వర్ మీద అకస్మాత్తుగా లోడ్ పడకుండా (Server overload నివారించవచ్చు) చాలా సురక్షితంగా మెసేజ్‌లు రీ-ప్రాసెస్ అవుతాయి.

# 4: Advanced Architecture & Tuning

RabbitMQ లెర్నింగ్‌లో మనం ఇప్పుడు అత్యంత ఆధునికమైన మరియు పవర్‌ఫుల్ అయిన **Phase 4 (Advanced Architecture & Tuning)** లోకి అడుగుపెట్టాము. లార్జ్-స్కేల్ అప్లికేషన్లలో డేటా సేఫ్టీ మరియు హై-పెర్ఫార్మెన్స్ కోసం వాడే మోడర్న్ క్యూ టైప్స్ గురించి తెలుగులో వివరంగా తెలుసుకుందాం!

---

## 1. Quorum Queues (క్వొరమ్ క్యూలు)

పాత వెర్షన్లలో RabbitMQ డేటాను సేఫ్ గా ఉంచడానికి **Mirrored Queues** వాడేవారు, కానీ వాటిలో కొన్ని పెర్ఫార్మెన్స్ సమస్యలు ఉండేవి. వాటికి బదులుగా ఇప్పుడు **Quorum Queues** వాడుతున్నారు.

- **పనితీరు:** ఇవి **Raft Consensus Algorithm** ఆధారంగా పనిచేస్తాయి. అంటే ఒక క్యూ డేటాను కేవలం ఒకే సర్వర్ లో కాకుండా, క్లస్టర్‌లోని పలు నోడ్స్‌లో (Multiple Nodes) సేవ్ చేస్తాయి.
- **High Availability (అధిక లభ్యత):** క్లస్టర్‌లోని మెయిన్ సర్వర్ (Leader) అకస్మాత్తుగా క్రాష్ అయినా సరే, మిగతా సర్వర్లు (Followers) వెంటనే అప్రమత్తమై రాఫ్ట్ అల్గోరిథం ద్వారా కొత్త లీడర్‌ను ఎన్నుకుంటాయి. దీనివల్ల ఏ మాత్రం డేటా లాస్ అవ్వకుండా సిస్టమ్ నిరంతరం రన్ అవుతుంది.
- **ఎప్పుడు వాడాలి:** ఫైనాన్షియల్ ట్రాన్సాక్షన్స్ లేదా ఆర్డర్ ప్రాసెసింగ్ లాంటి క్రిటికల్ అప్లికేషన్లలో డేటా అసలు పోకూడదనుకున్నప్పుడు Quorum Queues బెస్ట్ ఛాయిస్.

---

## 2. Stream Queues (స్ట్రీమ్ క్యూలు)

ఇది RabbitMQ లో సాధ్యమైనంత ఎక్కువ స్పీడ్ (High-throughput) మరియు ప్రత్యేక అవసరాల కోసం తెచ్చిన అడ్వాన్స్‌డ్ ఫీచర్. ఇది సరిగ్గా **Apache Kafka** లాగా పనిచేస్తుంది.

- **Append-Only Log:** ఇందులో మెసేజ్‌లు ఒకదాని తర్వాత ఒకటి లాగ్ ఫైల్ లాగా డిస్క్‌లో శాశ్వతంగా స్టೋರ್ అవుతాయి.
- **Non-Destructive Reading (డిస్ట్రాయ్ కాని రీడింగ్):** సాధారణ క్యూలలో కన్జ్యూమర్ మెసేజ్ చదవగానే అది క్యూ నుండి డిలీట్ అయిపోతుంది. కానీ స్ట్రీమ్ క్యూలలో కన్జ్యూమర్ మెసేజ్ చదివినా అది **డిలీట్ అవ్వదు**, అక్కడే ఉంటుంది.
- **Replayability (రీ-ప్లే చేయడం):** కావలాలంటే పాత మెసేజ్‌లను మళ్ళీ మొదటి నుండి లేదా కావలసిన ఆఫ్‌సెట్ (Offset) నుండి ఎన్నిసార్లయినా మళ్ళీ చదువుకోవచ్చు (Replay చేసుకోవచ్చు).
- **ఎప్పుడు వాడాలి:** రియల్-టైమ్ డేటా అనలిటిక్స్, లాగ్ కలెక్షన్, లేదా ఒకే డేటాను వేర్వేరు కన్జ్యూమర్లు వేర్వేరు సమయాల్లో చదవాల్సి వచ్చినప్పుడు స్ట్రీమ్ క్యూలు చాలా అద్భుతంగా పనిచేస్తాయి.

---

RabbitMQ లెర్నింగ్‌లో చివరి మరియు అత్యంత కీలకమైన **Phase 4 (Performance Tuning & Microservice Integration Patterns)** కి వచ్చేసాము! ప్రొడక్షన్ లెవెల్ అప్లికేషన్లలో సిస్టమ్ స్పీడ్‌గా, ఎక్కడా ఆగిపోకుండా (Bottlenecks లేకుండా) రన్ కావడానికి ఇవి చాలా ముఖ్యం. వీటిని తెలుగులో సులభంగా చూద్దాం!

---

## 1. Performance Tuning (పనితీరును మెరుగుపరిచే విధానాలు)

### Prefetch Count (QoS - కన్జ్యూమర్ బ్యాక్‌ప్రెషర్ కంట్రోల్)

- **సమస్య:** ఒక క్యూలో 10,000 మెసేజ్‌లు ఉంటే, RabbitMQ అన్నీ కలిపి ఒకే కన్జ్యూమర్‌కి ఒకేసారి పంపితే ఆ కన్జ్యూమర్ క్రాష్ అయిపోవచ్చు.
- **పరిష్ారం (Prefetch Count):** `qos` (Quality of Service) ద్వారా కన్జ్యూమర్ ఒకసారಿಗೆ ఎన్ని అన్‌క్యూడ్ (unacked) మెసేజ్‌లను మాత్రమే తీసుకోవచ్చో లిమిట్ సెట్ చేయవచ్చు (ఉదాహరణకు `prefetch_count = 10`). కన్జ్యూమర్ ఆ 10 మెసేజ్‌లను ప్రాసెస్ చేసి `ACK` ఇస్తేనే, RabbitMQ తర్వాతి మెసేజ్‌లను పంపుతుంది. దీనివల్ల కన్జ్యూమర్ మీద ఓవర్‌లోడ్ పడదు.

### Channel management and connection pooling

- **కనెక్షన్ vs చానెల్:** ప్రతిసారీ RabbitMQ తో కొత్త TCP కనెక్షన్ ఓపెన్ చేయడం చాలా ఖర్చుతో కూడుకున్నది (CPU & Network వృధా అవుతుంది). అందుకే ఒకే కనెక్షన్ లోపల బహుళ **Channels** వాడాలి.
- **Connection Pooling:** నోడ్.జెస్ (Node.js) లేదా జావా (Java) అప్లికేషన్లలో కనెక్షన్లను ముందుగానే క్రియేట్ చేసి పూల్ (Pool) లో ఉంచుతారు. అప్లికేషన్‌కి అవసరమైనప్పుడు ఆ పూల్ నుండి కనెక్షన్ తీసుకొని పని అయిపోయాక తిరిగి ఇచ్చేస్తారు.

### Batching publishes and acknowledgments

- ఒక్కో మెసేజ్‌ని విడివిడిగా పంపడం లేదా విడివిడిగా `ACK` ఇవ్వడం కంటే, కొన్ని మెసేజ్‌లను ఒకే **ಬ್ಯಾಚ್ (Batch)** గా కలిపి పంపడం లేదా అకనాలెజ్ చేయడం వల్ల నెట్‌వర్క్ ట్రాఫిక్ తగ్గి స్పీడ్ విపరీతంగా పెరుగుతుంది.

---

## 2. Microservice Integration Patterns (మైక్రోసర్వీసెస్ అనుసంధాన పద్ధతులు)

### Request-Reply (RPC Style over AMQP)

- సాధారణంగా RabbitMQ అనేది వన్-వే (One-way) కమ్యూనికేషన్ (పంపడం, మర్చిపోవడం). కానీ కొన్నిసార్లు ఒక సర్వీస్ మరో సర్వీస్‌కి రిక్వెస్ట్ పంపి రిప్లై కూడా వెయిట్ చేయాల్సి వస్తుంది.
- దీన్ని చేయడానికి **Correlation ID** మరియు **Reply-To Queue** వాడతారు. ప్రొడ్యూసర్ రిక్వెస్ట్‌తో పాటు ఒక టెంపరరీ రిప్లై క్యూ పేరు పంపుతుంది, కన్జ్యూమర్ పని పూర్తి చేశాక ఆ రిప్లై క్యూకి రెస్పాన్స్ పంపుతుంది.

### Saga Pattern (Orchestration vs Choreography)

మైక్రోసర్వీసెస్ ఆర్కిటెక్చర్‌లో ఒక డిస్ట్రిబ్యూటెడ్ ట్రాన్సాక్షన్ (ఉదాహరణకు: ఆర్డర్ ప్లేస్ చేయడం -> పేమెంట్ కట్ అవ్వడం -> షిప్పింగ్ చేయడం) ఫెయిల్ అయితే ఎలా హ్యాండిల్ చేయాలి?

- **Choreography (సమన్వయం):** ప్రతి సర్వీస్ ఒక ఈవెంట్‌ని వింటోంది, తన పని అయ్యాక మరో ఈవెంట్‌ని పంపిస్తుంది (సెంట్రల్ కంట్రోలర్ ఉండదు).
- **Orchestration (డైరెక్టర్/కంట్రోలర్):** ఒక సెంట్రల్ 'Saga Orchestrator' సర్వీస్ ఉంటుంది. అదే అన్నీ సర్వీసెస్‌కి ఆర్డర్స్ ఇస్తుంది, ఏదైనా ఫెయిల్ అయితే వేరే సర్వీసెస్‌కి 'Compensating Transaction' (ఉదాహరణకు: పేమెంట్ రీఫండ్ చేయడం) చేయమని చెబుతుంది. RabbitMQ ఈ ఈవెంట్లను ఎక్స్చేంజ్ల ద్వారా పాస్ చేయడానికి మెయిన్ రోల్ ప్లే చేస్తుంది.

### Event-Driven Architecture (EDA)

- సర్వీసెస్ అన్నీ నేరుగా మాట్లాడుకోకుండా, "ఏదైనా ఒక ముఖ్యమైన సంఘటన (Event) జరిగినప్పుడు" (ఉదా: `UserSignedUp`, `OrderPlaced`) ఆ ఈవెంట్‌ని RabbitMQ ఎక్స్ఛేంజ్కి పంపిస్తాయి. ఆ ఈవెంట్ కావాల్సిన ఏ సర్వీసెస్ అయినా సరే వాటిని సబ్‌స్క్రైబ్ చేసుకొని తమ పని తాము చేసుకుంటాయి. ఇది సిస్టమ్‌ని చాలా లూజ్లీ కపుల్డ్ (Loosely coupled) మరియు స్కేలబుల్‌గా ఉంచుతుంది.

# 5: Production Operations & DevOps

RabbitMQ లెర్నింగ్‌లో అత్యంత కీలకమైన చివరి దశ **Phase 5 (Production Operations & DevOps)** కి వచ్చేశాము! ప్రొడక్షన్ ఎన్విరాన్‌మెంట్‌లో RabbitMQ ని మేనేజ్ చేయడానికి, డేటా సేఫ్టీగా ఉంచడానికి మరియు సెక్యూరిటీని మెసూర్ చేయడానికి ఇవి చాలా ముఖ్యం. వీటిని తెలుగులో సులభంగా చూద్దాం!

---

## 1. Clustering & High Availability (క్లస్టరింగ్ మరియు హై అవైలబిలిటీ)

### Multi-node Cluster Design (బహుళ-నోడ్ క్లస్టర్ డిజైన్)

- ఒకే RabbitMQ సర్వర్ క్రాష్ అయితే మొత్తం అప్లికేషన్ ఆగిపోకుండా ఉండటానికి, బహుళ సర్వర్లను (Nodes) కలిపి ఒకే **Cluste** గా ఏర్పాటు చేస్తారు.
- క్లస్టర్‌లో ఎక్స్ఛేంజెస్, బైండింగ్స్ కామన్ గా ఉంటాయి, కానీ క్యూలు మాత్రం డిఫాల్ట్ గా ఒకే నోడ్ పై ఉంటాయి (మనం ముందు చర్చించిన Quorum Queues వాడితే ఆ సమస్య ఉండదు, అవి ఆటోమేటిక్‌గా అన్ని నోడ్స్‌లోనూ సింక్ అవుతాయి).

### Network Partitions & Split-Brain Scenarios

- ఇంటర్నెట్ లేదా నెట్‌వర్క్ ప్రాబ్లమ్ వల్ల క్లస్టర్‌లోని సర్వర్లు రెండు విభిన్న గ్రూపులుగా విడిపోవడాన్ని **Network Partition** అంటారు.
- ఇలా జరిగి రెండు వైపులా ఉన్న సర్వర్లు వేర్వేరుగా డేటాను మార్చుకుంటే **Split-Brain** సమస్య వస్తుంది. అంటే డేటా కరప్ట్ అయ్యే ఛాన్స్ ఉంటుంది.

### Pause-Minority Recovery Policies

- నెట్‌వర్క్ పార్టిషక్ ఏర్పడినప్పుడు, ఏ సర్వర్ గ్రూప్‌లో అయితే తక్కువ నోడ్స్ (Minority) ఉంటాయో, ఆ సర్వర్లు ఆటోమేటిక్‌గా తాము పాజ్ (Pause) అయిపోతాయి. ఎక్కువ నోడ్స్ ఉన్న గ్రూప్ (Majority) మాత్రమే రన్ అవుతుంది.
- నెట్‌వర్క్ మళ్ళీ సరిగ్గా కుదిరాక, పాజ్ అయిన సర్వర్లు ఆటోమేటిక్‌గా మెయిన్ గ్రూప్ నుండి డేటాను సింక్ చేసుకుని నార్మల్ అవుతాయి. ఇది డేటా లాస్ కాకుండా కాపాడుతుంది.

## 2. Federation & Shovel Plugins (ఫెడరేషన్ మరియు షొవెల్ ప్లగిన్స్)

ఒకే క్లస్టర్ కాకుండా, వేర్వేరు ప్రాంతాలలో (ఉదాహరణకు: ముంబై డేటా సెంటర్ మరియు సింగపూర్ డేటా సెంటర్) ఉన్న వేర్వేరు RabbitMQ క్లస్టర్ల మధ్య మెసేజ్‌లను పంచుకోవడానికి ఇవి వాడతారు.

- **Federation Plugin:** ఇది ఆటోమేటిక్‌గా ఒక క్లస్టర్ నుండి మరో క్లస్టర్‌కి అవసరమైన మెసేజ్‌లను (లేదా ఎక్స్ఛేంజ్ డేటాను) కాపీ చేసుకుంటుంది (WAN-friendly).
- **Shovel Plugin:** ఇది ఒక పైప్‌లాంటిది. ఒక సోర్స్ క్యూ నుండి మెసేజ్‌లను తీసి, మరో క్లస్టర్‌లోని డెస్టినేషన్ క్యూకి నమ్మకంగా (Reliable) బదిలీ చేస్తుంది.

## 3. Monitoring & Security (మానిటరింగ్ మరియు భద్రత)

### Prometheus & Grafana Integration

- ప్రొడక్షన్‌లో RabbitMQ పనితీరును లైవ్‌లో చూడటానికి ప్రొమెథియస్ (Prometheus) మరియు గ్రేఫానా (Grafana) వాడతారు.
- **ముఖ్యమైన మెట్రిక్స్:** క్యూ డెప్త్ (Queue depth - క్యూలో ఎంత డేటా నిండి ఉంది), పబ్లిష్/కన్జూమ్ రేట్స్ (సెకనుకి ఎన్ని మెసేజెస్ వెళ్తున్నాయి), మరియు మెమరీ అలార్మ్స్ (RAM నిండిపోతుందా లేదా).

### TLS/SSL Encryption, VHosts & RBAC

- **TLS/SSL Encryption:** అప్లికేషన్ నుండి RabbitMQ కి వెళ్లే డేటా ఎవరికీ హ్యాక్ అవ్వకుండా ఎన్‌క్రిప్ట్ చేస్తుంది.
- **VHosts (Virtual Hosts):** ఒకే RabbitMQ సర్వర్ లోపల వేర్వేరు ప్రాజెక్ట్‌ల కోసం వేర్వేరు వర్చువల్ స్పేస్‌లను (వాల్స్ లాంటివి) క్రియేట్ చేయడం. దీనివల్ల ఒక ప్రాజెక్ట్ డేటా మరో ప్రాజెక్ట్‌కి కలవదు.
- **RBAC (Role-Based Access Control):** ఏ యూజర్‌కి ఏ క్యూ మీద పర్మిషన్స్ ఉండాలి (ఎవరు కేవలం రీడ్ చేయాలి, ఎవరు పబ్లిష్ చేయాలి) అని కంట్రోల్ చేసే యూజర్ మేనేజ్‌మెంట్.

# Code example (nodejs)

RabbitMQ తో Node.js లో ఎలా పని చేయాలో ఒక సింపుల్ మరియు క్లియర్ కోడ్ ఉదాహరణ చూద్దాం. దీని కోసం మనం বহుల ప్రాచుర్యం పొందిన **`amqplib`** లైబ్రరీని వాడుతాం.

ఇక్కడ మనం ఒక **Producer** (మెసేజ్ పంపేది) మరియు ఒక **Consumer** (మెసేజ్ తీసుకొని ప్రాసెస్ చేసేది) కోడ్ చూద్దాం.

---

### 1. ముందుగా ప్యాకేజీని ఇన్‌స్టాల్ చేయండి

మీ ప్రాజెక్ట్ ఫోల్డర్‌లో టెర్మినల్ ఓపెన్ చేసి ఈ కమాండ్ రన్ చేయండి:

```bash
npm install amqplib

```

---

### 2. Producer కోడ్ (`producer.js`)

ఇది RabbitMQ క్యూకి మెసేజ్‌లను పంపుతుంది.

```javascript
const amqp = require("amqplib");

async function sendMessage() {
  try {
    // 1. RabbitMQ సర్వర్‌కి కనెక్ట్ అవ్వండి (Docker లో రన్ అయ్యే లోకల్ URL)
    const connection = await amqp.connect("amqp://localhost");
    const channel = await connection.createChannel();

    // 2. ఒక క్యూని క్రియేట్ చేయండి (Durable: true అంటే సర్వర్ రీస్టార్ట్ అయినా క్యూ పోదు)
    const queueName = "task_queue";
    await channel.assertQueue(queueName, { durable: true });

    // 3. పంపవలసిన మెసేజ్
    const message = "হ্যালো RabbitMQ! ఇది Node.js నుండి పంపిన మెసేజ్.";

    // 4. క్యూకి మెసేజ్ పంపండి (persistent: true అంటే మెసేజ్ డిస్క్ లో సేవ్ అవుతుంది)
    channel.sendToQueue(queueName, Buffer.from(message), { persistent: true });

    console.log(`[x] మెసేజ్ విజయవంతంగా పంపబడింది: "${message}"`);

    // 5. కొద్దిసేపటి తర్వాత కనెక్షన్ క్లోజ్ చేయండి
    setTimeout(() => {
      connection.close();
      process.exit(0);
    }, 500);
  } catch (error) {
    console.error("Error:", error);
  }
}

sendMessage();
```

### 3. Consumer కోడ్ (`consumer.js`)

ఇది క్యూ నుండి మెసేజ్‌లను రిసీవ్ చేసుకొని ప్రాసెస్ చేస్తుంది.

```javascript
const amqp = require("amqplib");

async function receiveMessages() {
  try {
    // 1. RabbitMQ సర్వర్‌కి కనెక్ట్ అవ్వండి
    const connection = await amqp.connect("amqp://localhost");
    const channel = await connection.createChannel();

    const queueName = "task_queue";
    await channel.assertQueue(queueName, { durable: true });

    // Prefetch count: ఒకసారಿಗೆ ఒక కన్జ్యూమర్ కేవలం 1 మెసేజ్ మాత్రమే తీసుకోవాలని లిమిట్ పెట్టడం (QoS)
    channel.prefetch(1);

    console.log(
      `[*] క్యూ (${queueName}) నుండి మెసేజ్ కోసం ఎదురుచూస్తోంది... బ్రేక్ చేయడానికి CTRL+C నొక్కండి.`,
    );

    // 2. క్యూ నుండి మెసేజ్‌లను విని స్వీకరించడం
    channel.consume(
      queueName,
      (msg) => {
        if (msg !== null) {
          const messageContent = msg.content.toString();
          console.log(`[x] మెసేజ్ స్వీకరించబడింది: "${messageContent}"`);

          // ఇక్కడ మీ బిజినెస్ లాజిక్ (ప్రాసెసింగ్) రాసుకోవచ్చు
          // ఉదాహరణకు: 2 సెకండ్లు పడుతుందని అనుకుందాం
          setTimeout(() => {
            console.log("[✔] మెసేజ్ ప్రాసెసింగ్ పూర్తయింది!");

            // 3. Manual Acknowledgment: పని పూర్తయినట్లు RabbitMQ కి చెప్పడం (ACK)
            channel.ack(msg);
          }, 2000);
        }
      },
      { noAck: false },
    ); // noAck: false అంటే మ్యాన్యువల్ అకనాలెడ్జ్‌మెంట్ వాడమని అర్థం
  } catch (error) {
    console.error("Error:", error);
  }
}

receiveMessages();
```

### దీన్ని ఎలా రన్ చేయాలి?

1. కొత్త టెర్మినల్ ఓపెన్ చేసి **Consumer** ని రన్ చేయండి (ఇది క్యూ కోసం వెయిట్ చేస్తూ ఉంటుంది):

```bash
node consumer.js

```

2. మరొక కొత్త టెర్మినల్ ఓపెన్ చేసి **Producer** ని రన్ చేయండి:

```bash
node producer.js

```

ప్రొడ్యూసర్ మెసేజ్ పంపగానే, కన్జ్యూమర్ దాన్ని రిసీవ్ చేసుకొని ప్రాసెస్ చేసి `ACK` ఇవ్వడం మీరు స్క్రీన్ పై చూడవచ్చు! ఇందులో మీకు ఏవైనా లైన్స్ అర్థం కాకపోతే అడగండి, మరింత వివరంగా వివరిస్తాను.
